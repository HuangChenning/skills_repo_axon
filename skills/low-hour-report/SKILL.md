# 低报工排查

> **数据源**：`mes statistics list` 中的实际报工记录（`type=1`，实施计划），按 `rid`（计划 ID）聚合 `taskTime`。**不得使用 `plan list` 的 `executorList.taskTime`**——那是计划分配工时，不是实际报工工时。
>
> **⚠️ `mes plan list --start-date/--end-date` 是"完全包含"过滤，不是"时间重叠"过滤**（2026-09-01 实测确认）：只返回 `startDate` 和 `endDate` **都**落在查询区间内的计划，跨查询窗口边界的长周期计划（尤其是"进行中"的维保/巡检项目）会被漏掉而不报错。**禁止用它来拉取参与统计的计划池**——正确做法见步骤2。

## MES 登录

本技能所有数据均通过 `mes` CLI 拉取。使用前需先完成登录并确认 token 有效：

```bash
mes auth login
mes auth status
```

## 一、判定标准

| 分类 | 条件 | 标记 |
|------|------|------|
| 零报工 | 实际报工总工时 = 0 | 🔴 零报工 |
| 极低报工 | 0 < 实际报工总工时 < 20h | 🟡 极低报工 |
| 正常 | 实际报工总工时 ≥ 20h | — |

阈值 20h 为默认值，用户可指定其他阈值（如 10h、30h）。

**统计范围**：状态（`statusDesc`）为「已逾期未结束」或「结束」的计划**不参与**零报工/极低报工统计。因此步骤2**拉取数据**时只需覆盖「进行中」（`status=1`）「未开始」（`status=0`）两种状态。

**⚠️ 「未开始」不等于会进入分类（易读错，2026-09-01 明确）**：步骤2拉「未开始」只是为了在最终报告里展示「排除计划明细」，**不代表它会参与零/极低/正常三档分类**。无论 `startDate` 是未来还是已过，「未开始」状态的计划在步骤4**永远**被单独列出、排除在分类之外（未来的标「尚未到执行时间」，已过的标「状态异常」，见下方判定标准/步骤4）——**真正会被判定为零/极低/正常报工的，只有「进行中」状态的计划**。不要因为这句话里出现了「未开始」字样，就把它当成会被分类为零报工的候选。

**计划类型排除（2026-09-01 新增）**：`checkTypeDesc`（计划类型）为「售前POC」或「内部事项」的计划**不参与**统计——这两类不是常规客户服务合同（售前POC 是销售前技术验证，内部事项是内部工作），不适用报工合规检查，见步骤2。

**状态异常防御（2026-09-01 新增，防御性规则）**：`statusDesc` 为「未开始」但 `startDate` 已经过去（不晚于当前时刻）的计划**不参与**统计——正常情况下 MES 系统应在 `startDate` 过后把状态转成「已逾期未结束」，若仍停留在「未开始」属于状态滞后/异常，语义上等同「还没真正启动」，不应作为报工检查对象。2026-09-01 实测系统里全部 75 个「未开始」计划的 `startDate` 都还在未来，当前无实例命中——这条是防御未来出现该情况的兜底规则，不是修复已发现的真实 bug。

**⚠️ 不按计划总时长排除（2026-09-01 明确，曾短暂加过 90 天阈值又被撤销）**：只要计划状态是「进行中」或「未开始」、且计划周期与查询窗口有时间重叠，无论计划自身总时长多长（哪怕是跨年的维保/驻场/现场人天框架合同），都**参与**统计——按该计划**在查询窗口内**的实际报工工时判定零/极低/正常，三档都要展示，不得只挑零报工/极低报工两档、隐藏正常档。
- 这意味着跨年长期框架合同如果在查询窗口内确实没有报工，会被统计为零报工——这是用户明确要求保留的行为，**不要**因为担心"长周期合同噪音"而自行加时长阈值过滤。如报告中该类计划占比很高，如实说明其构成（如 `checkTypeDesc` 分布），但不要静默剔除。

## 二、查询流程

### 步骤1：解析时间范围

将用户输入的时间范围转换为 `YYYY-MM-DD` 格式：

| 用户表述 | 转换（示例为 2026 年） |
|---------|---------------------|
| 「最近3个月」 | 当前日期往前推3个月 → 当月1日 ~ 今天 |
| 「Q2」「4月到6月」 | 2026-04-01 ~ 2026-06-30 |
| 「4月1日~6月30日」 | 2026-04-01 ~ 2026-06-30 |
| 「上个月」 | 上月1日 ~ 上月最后一天 |
| 「今年」 | 2026-01-01 ~ 2026-12-31 |

默认当年至今。年份未指定时默认当年。对于长周期查询（超过 3 个月），告知用户需要分页拉取全部报工记录，耗时可能较长。

**表外的相对时间表述**（如「最近半年」「最近30天」「上季度」「去年」）按同样规则换算，不要因为没在表里就瞎猜或跳过确认：「最近N个月/N天」= 当前日期往前推N个月/天 ~ 今天；「上季度」= 按当前月份定位所属季度再往前推一个季度的完整起止日期；无法确定归属年份或语义有歧义时，先问用户而不是直接执行。

### 步骤2：拉取参与统计的计划池（进行中 / 未开始，按 status 不带日期拉全量）

**不要用 `--start-date/--end-date` 拉取参与统计的计划**（见上方⚠️说明，会漏掉跨窗口边界的计划）。由于「已逾期未结束」「结束」两种状态本就被排除出统计（见一、判定标准），只需精确覆盖「进行中」（`status=1`）「未开始」（`status=0`）两种状态即可——2026-09-01 实测系统总量约850个（进行中约770+未开始约75），可无日期限制逐页拉全量。**若某次执行发现该总量增长到数万级**（比如系统运营多年后），逐页全量拉取会变慢甚至不现实，需要重新评估方案（如按月/季度分批拉 `--status` 且带一个足够宽但仍远小于全表的日期兜底范围），届时先向用户说明再改，不要为了省时间自行加严过滤条件导致漏检：

```bash
# 进行中
mes -o json plan list --status 1 --page-size 100 --page 1   # 逐页拉取直到覆盖全部
# 未开始
mes -o json plan list --status 0 --page-size 100 --page 1   # 逐页拉取直到覆盖全部
```

**本地重叠过滤**：只保留 `plan.startDate <= 查询窗口结束` 且 `plan.endDate >= 查询窗口开始` 的计划（时间区间有交集即保留，不要求完全包含在窗口内）。**不做时长过滤**——无论计划自身周期多长（含跨年框架合同）都保留，进入下一步分类。

**本地类型过滤**：`checkTypeDesc` 为「售前POC」或「内部事项」的计划剔除，不参与分类（计入「排除计划」，标注排除原因，见三、输出格式）。

将过滤后的结果保存为以 `id` 为 key 的字典，用于后续关联元数据。

**提取字段**：`id`, `title`, `companyName`, `contractName`, `statusDesc`, `startDate`, `endDate`, `checkTypeDesc`, `executorList[].executorName`。`contractName` 等字段为 `null` 时报告里留空展示，不得编造或用其他字段拼凑替代。

### 步骤2b（可选）：拉取排除计划明细（仅用于报告展示，不参与统计）

「已逾期未结束」「结束」状态的计划不影响统计结果，只在报告的"排除计划明细"里展示。可继续沿用 `--start-date/--end-date` 拉取（该接口的完全包含限制在此处可接受——即便漏掉个别跨窗口边界的已排除计划，也不影响统计正确性，只影响展示的完整度）：

```bash
mes -o json plan list \
  --start-date "<开始日期>" \
  --end-date "<结束日期>" \
  --page-size 100 --page 1
```

逐页拉取，筛选 `statusDesc` 为「已逾期未结束」或「结束」的记录用于展示。**「售前POC」「内部事项」类型的排除计划不需要额外拉取**——它们本就在步骤2的 `status=1/0` 全量池里，只是被本地类型过滤剔除，直接复用即可，标注对应排除原因。

### 步骤3：拉取全部实际报工记录（核心数据）

```bash
mes -o json statistics list \
  --from "<开始日期>" \
  --to "<结束日期>" \
  --page-size 200 --page 1
```

**必须将 JSON 重定向到临时文件**，用 `python3` 逐页解析。不要依赖终端截断输出。

对每页记录：
1. 筛选 `type == 1`（实施计划报工）
2. 按 `rid`（计划 ID）累加 `taskTime`
3. 记录每条报工的 `executorName` 用于展示

**⚠️ 禁止按 `reviewStatus`（审批状态）或 `signStatus`（签字状态）过滤（2026-09-01 明确）**：只要是 `type==1` 的报工记录，不论「待审批/已审批/待签字/已签字」都算作已报工、计入 `taskTime` 汇总。原因：实测数据里 98% 记录长期处于「待审批」「待签字」（审批/签字是后置流程，滞后于报工本身），按此过滤会把几乎所有人都误判成零报工。

### 步骤4：关联并分类

步骤2产出的计划池已经只包含「进行中」「未开始」、与查询窗口重叠、且计划类型不是「售前POC」「内部事项」的计划（已排除「已逾期未结束」「结束」，不限时长）。对池中**每一个计划**：
- 如果 `plan.id` 在步骤3的聚合结果中 → 取其 `taskTime` 总和
- 如果不在 → 实际报工为 0（**零报工**）

然后按判定标准分为零报工、极低报工、正常三类；其中状态为「未开始」的计划单独列出（不计入分类，见四、输出规则第4条）——`startDate` 晚于当前时刻的标「尚未到执行时间」，`startDate` 已过的标「状态异常（未开始但已过起始时间）」，两种都不进分类，不要只处理前者漏了后者。

### 步骤5：输出报告

## 三、输出格式

```markdown
## 报工排查报告

**时间范围**：2026-04-01 ~ 2026-06-30
**计划总数**：N 个（参与统计的计划数，已剔除下方排除计划）
**排除计划数**：K 个（未开始-未来计划 + 未开始-状态异常 + 已逾期未结束/结束 + 售前POC/内部事项）
**实际报工记录数**：M 条（type=1）

| 分类 | 数量 | 占比 |
|------|------|------|
| 🔴 零报工 | X | X% |
| 🟡 极低报工（< 20h） | Y | Y% |
| 正常（≥ 20h） | Z | Z% |
```

### 🔴 零报工明细


### 🟢 正常明细

## 四、输出规则

> **⚠️ 定时任务调用时：日期合理性自检（防 catch-up 补跑误发，2026-08 起强制）**
>
> 本技能被「每月 1 号」月初（770c0c67）和「每月 22-31 号周一」月末（bdbfeeb0）定时任务调用并发送邮件。**非预期触发（gateway 停机后 catch-up 补跑、jobs.json 恢复、手动运行）会在错误日期执行**，此时查询范围错误且会误发邮件。**调用方 cron 的 prompt 已含日期自检**（月初=1 号 / 月末=22-31 号周一，非运行日直接 `[SILENT] exit 0`），运行本技能前必须先通过该自检；若作为独立命令被手动调用，也先确认查询意图。

1. **必须完整读取**：statistics 和 plan list 的 JSON 输出必须通过临时文件 + `python3` 完整解析，不得依赖终端截断。完成后删除临时文件。
2. **Top N 截断**：零报工、极低报工或正常任一分类超过 30 条时，该分类仅展示前 30 条并标注「还有 X 条未展示，可要求查看完整列表」。
3. **阈值可调**：用户指定了阈值（如「不足 10 小时」）时，使用用户指定的阈值替代默认的 20h。
4. **计划范围排除**：以下四类计划不计入零报工/极低报工统计，各自在报告中单独列出并标注排除原因，不混入正常分类：
   - 计划 `startDate` 晚于当前时刻且状态为「未开始」→ 标注「尚未到执行时间」
   - 状态为「未开始」但 `startDate` 已过（不晚于当前时刻）→ 标注「状态异常（未开始但已过起始时间）」——防御性规则，见一、判定标准
   - 状态为「已逾期未结束」或「结束」→ 标注「状态已排除（已逾期未结束/结束）」
   - `checkTypeDesc` 为「售前POC」或「内部事项」→ 标注「计划类型已排除（售前POC/内部事项）」
5. **正常档也要展示**：三、输出格式的统计表里「正常（≥20h）」不能只给数量，必须像零报工/极低报工一样有对应明细表格（计划ID/标题/客户/合同/计划类型/工时/计划时间/状态），除非用户明确表示只要异常清单。
6. **不做时长排除**：不得因为计划总时长长（跨年维保/驻场/现场人天框架合同）而将其排除出统计——只要状态是「进行中」「未开始」且与查询窗口有时间重叠，一律参与分类。若零报工/极低报工中长周期框架合同占比较高，如实在报告中说明其 `checkTypeDesc`/时长构成，但不得静默剔除（历史上曾加过 90 天阈值又被用户明确撤销，不要再加）。
